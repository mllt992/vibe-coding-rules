# AI 能力边界与对策

> 这是 vibe coding 的核心常识：**AI 不是无所不能的。**
> 它有几类专属的失败模式，与人写代码的失败模式不同。识别它们，才能 vibe 得稳。

---

## 一、API 幻觉（Hallucinated APIs）

### 症状
- AI 自信地写出一个**根本不存在的函数 / 库 / 配置项**
- 看起来合理（名字像、签名像、返回值像）
- 代码"看起来能跑"但跑不通

### 为什么发生
- AI 训练数据是过去某个时间点的快照——之后的 API 变化它不知道
- AI 的本质是"预测下一个 token"——在不熟悉的库上，它倾向于"猜一个最合理的写法"
- 类似 API 在不同库里命名相似（如 `axios.get` vs `fetch`），AI 会混淆

### 高发场景
- 小众 / 新版本的库
- 最近 1-2 年才出的功能
- 同一概念在不同框架里 API 不同（HTTP 客户端、ORM、测试框架）
- 配置选项（特别是 webpack、tsconfig、各种工具的配置项）

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 写陌生库代码前**先查官方文档**，禁止凭记忆 | 让 AI 把"我用了这些 API 引用，来源：xxx 文档第 N 节"写到 PR 描述 |
| 把第三方库版本写在 CLAUDE.md 项目基本情况 | 涉及最近发布的库，主动提供官方文档链接给 AI |
| 怀疑某 API 可能不存在时，**显式查阅** | 看到 AI 用了陌生 API，先跑一下确认能调通 |

### 红线
- 写完不跑就交付
- "我记得这个 API 是这样的"——记忆不是事实
- 用错的 API + 编造的注释自圆其说（**这是最危险的**）

## 二、过时知识（Stale Knowledge）

### 症状
- 用 N 年前流行的写法（如 React 用 class component；Vue 2 的 mixin；Node 用 require）
- 用早已 deprecated 的 API
- 推荐的库已不再维护

### 为什么发生
- 训练数据有时间截止点（参考 AI 自己说的 knowledge cutoff）
- 主流社区写法演变快，AI 学的是历史均值
- "过时但能跑"很难自己发现

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 涉及版本敏感的代码，明确询问"项目用的是哪个版本？" | 在 CLAUDE.md 项目基本情况里写清楚关键依赖的**主版本号** |
| 选库前**主动查现状**：维护状态、社区评价、最新文档 | 关注主流社区的最新最佳实践，发现 AI 用了过时写法立即纠正 |

## 三、过度自信（Overconfidence）

### 症状
- AI 用同样的语气表达"我确定的事"和"我猜的事"
- 没有"我不确定"的明示
- 错误代码用很流畅的中/英文包装，**看起来太合理而难以怀疑**

### 为什么发生
- 模型训练目标是"流畅 + 看起来对"，而不是"诚实标注置信度"
- AI 没有内省机制告诉自己"这部分我可能错"
- 文风习惯：肯定句比"可能…大概…"更受训练奖励

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| **主动标注置信度**：高 / 中 / 低 / 不确定，特别是关键决策点 | 看到 AI 的关键判断没标注置信度，反问"这点你多确定？" |
| 不确定的点显式列出来 | 流畅的代码不等于正确的代码——**逐字看关键逻辑** |
| 用"假设 X 是 Y"的句式标注未验证假设 | 让 AI 写"如果 X 实际上不是 Y，会发生什么" |

### 自测语句（AI 应养成习惯）

```
- 关于 API 接口契约 → 高置信度（已查文档）
- 关于业务规则的"满 100 减 10"边界 → 低置信度，需开发者确认是否含 100
- 关于 React 19 新 hook 用法 → 中置信度，建议跑测试验证
```

## 四、上下文漂移（Context Drift）

### 症状
- 长会话里，AI 忘了最初的约定
- 反复指出同一类错误，AI 改了又犯
- 越往后回复越偏离原任务
- 任务超过半小时后产出质量明显下降

### 为什么发生
- 上下文窗口有限，旧消息可能被压缩/丢失
- 任务一长，关键约束被淹没在大量代码片段中
- 后期对话往往是细节调整，AI 容易"沉迷细节"忘了大方向

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 大任务**主动总结当前状态**，特别是关键约束 | 长会话每过半小时让 AI"总结一下我们达成的共识" |
| 用 Task / Todo 系统持久化进度（不依赖记忆） | 关键约定**写进 CLAUDE.md** 或 docs/，不要只在对话里说 |
| 重要约束**反复重申**，不要"说过一次就指望记得" | 任务过大时**起新会话**，把核心约束作为开场白 |

### 何时该起新会话
- 主任务已完成，准备切下一个不相关主题
- 当前会话超过 2 小时
- 反复出现同类错误（说明 AI 已经"漂走"）
- AI 开始重复之前说过的话

## 五、伪装完成（Pretending Done）

### 症状
- AI 报"已完成"但实际：测试没跑 / 自检没做 / 文档没更新
- "看起来跑通了" + 一堆 caveat（"如果这个不行你再告诉我"）
- 在自己跳过的步骤上"含糊带过"

### 为什么发生
- AI 没有内置的"完成度"度量，凭"产出量"判断
- 流畅地说"完成"比诚实地说"做了 80%"更容易出口
- 开发者一句"再快点"可能让 AI 跳过繁琐步骤来取悦

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 用 `docs/90_最佳实践/交付前自检清单.md` **逐条勾**，未勾完不能说"完成" | 听到"完成了"先反问"自检清单都打勾了吗？" |
| **明确披露**：本次做了什么 / 跳过了什么 / 为什么跳过 | 不被"完成了"的修辞欺骗，要求看具体证据（自检结果、测试输出） |
| 完成 = 可验证的产出，不是口头声明 | 关键任务结束前手动跑一遍验证 |

## 六、范围蔓延（Scope Creep）

### 症状
- 任务是改 BUG，AI 顺手优化了一堆"看着不顺眼"的代码
- 单个 PR 同时含新功能 + BUG 修复 + 重构
- 改动文件数远超预期

### 为什么发生
- AI 看到"明显的问题"很难不修
- "顺手改一下"成本低，但累加效应大
- 没有强约束时，AI 倾向于"做得更多 = 更努力"

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 严格"本次任务清单"原则，范围外问题记录到 `docs/03_问题记录/技术债.md` | 看到 PR 文件数超预期立即问"这些都是本次任务必需的吗？" |
| 顺手发现的问题**只记录不修** | 在指令中显式说"只改 X，其他不要碰" |

## 七、被动重复（Repeating without Thinking）

### 症状
- 用户指出错误，AI 道歉后再次犯同样的错
- 三轮修改后回到第一轮的代码
- "你说的对，让我修一下…" 然后改了别的地方

### 为什么发生
- 注意力分散在大量上下文中，关键反馈被稀释
- 后续生成时部分依赖之前的错误版本作为参考
- "道歉"作为社交润滑剂而非真正修复信号

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 用户纠错后，**先复述错在哪 + 为什么错**，再改 | 看到第二次犯同错，**起新会话**或**直接给最小复现** |
| 关键纠错点**写进 CLAUDE.md 或 docs/**，不依赖会话记忆 | 不要"你再改一下"，而要"把 X 改成 Y，因为 Z" |

## 八、复杂度欺骗（Plausible-Looking Complexity）

### 症状
- AI 写出一段"很专业"的复杂代码
- 包含大量 try-catch、抽象类、设计模式
- 但实际上简单的写法就能达成目的

### 为什么发生
- 训练数据里"复杂代码"经常出现在"高级教程"中，AI 学到"复杂 = 高级"
- 用户问"如何 X"，AI 倾向于给"完整方案"而不是"最小方案"
- 抽象层、设计模式名词显得专业

### 对策
| 给 AI 的对策 | 给开发者的对策 |
|---|---|
| 默认走**最简实现**，复杂方案需要先说明"为什么需要" | 看到没必要的抽象层（XxxFactory / XxxStrategy）问"为什么不直接写" |
| YAGNI（You Aren't Gonna Need It）—— 不为未来需求过度设计 | 砍掉用不上的扩展点 |

## 九、应用：AI 与开发者的"防御性协作"

### AI 侧
1. 每次开始任务先在脑中过一遍上面九条："我这次最可能踩哪个？"
2. 任务中段做一次自审："我有没有过度自信？有没有偏题？"
3. 任务结束前再对一遍交付前自检清单

### 开发者侧
1. 不被 AI 流畅的语言欺骗——真假在代码，不在描述
2. 关键决策点反问"这点你多确定？"
3. 长会话定期 reset，把约定固化到文档
4. 看 PR 时假设 AI 可能错，去找它哪里可能错

## 十、自检（AI 任务收尾时自问）

- [ ] 我用的 API / 库我是真的查过文档了，还是凭记忆？
- [ ] 我用的写法是不是已经过时了？（如有疑虑，请开发者确认）
- [ ] 我有没有把"我猜的"用"我确定的"语气说出来？
- [ ] 我有没有偏离会话开头的约定？
- [ ] 我说"完成了"是真的完成了，还是有跳过的步骤？
- [ ] 我有没有顺手改无关代码？
- [ ] 用户上次纠正过的错，我有没有再犯？
- [ ] 我的方案是不是过于复杂了？
