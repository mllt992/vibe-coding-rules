# 105 · 原型协同开发工作流程

> **触发条件**：开发者提供 HTML / Figma / 设计稿原型（可选附 Markdown PRD），要求落地到当前系统。
> **核心思想**：**原型会撒谎。**它用 mock 数据回避空/错/加载态，用独立样式回避设计系统，用静态页面回避状态机、路由和权限。
> 必须先**三方对齐**（PRD ↔ 原型 ↔ 现有代码库）再写代码，否则会产出"看着像原型但跑不通"的代码，后期返工。
>
> **与 100 / 101 的关系**：本流程是**前置增强**，不替代它们。
> - 新功能且有原型：先走 105 (1)~(5)，再回到 100 (6) 测试 / (7) 审查 / (8) 归档
> - 已有功能改造且有原型：先走 105 (1)~(5)，再回到 101 的回归与测试步骤
>
> **适用任务等级**（按 CLAUDE.md §2 定级）：
> - 标准 / 高风险任务：完整走
> - 小任务（改一个原型页面的小片段、< 100 行、无接口契约变更）：走 (2) 三方对齐 + (3) 拆解映射，跳过 (5) 双轨验收的归档项
> - 微改动（改文案、改颜色一处）：本工作流不适用，直接做

---

## 步骤总览

```
(1) 物料盘点  →  (2) 三方对齐（卡点：差异/缺口清单确认）  →
(3) 拆解映射  →  (4) 分层落地（骨架 → 数据/状态 → 边缘态）  →
(5) 双轨验收  →  进入 100 §6 测试 / §7 审查 / §8 归档
```

---

## (1) 物料盘点

### 做什么
- 收齐：HTML 原型文件、PRD（如有）、参考截图、设计令牌 / 设计系统文档（如有）
- 登记版本：原型版本号、PRD 版本号、是否定稿（未定稿的原型不开工）
- 通读一遍，记下"原型截图缺哪些页面 / PRD 缺哪些章节"

### 缺料即停
- 原型只截了主流程，没有错误/空/加载态截图 → 问开发者要补
- PRD 提到的功能在原型上找不到对应页面 → 先澄清
- 设计令牌（颜色、字号、间距、圆角、阴影）项目里没有、原型也没标 → 必须先对齐

### 产出
- 在差异/缺口清单（见下一步）的"物料"小节登记版本号和缺料项

## (2) 三方对齐 ⚠️ 卡点

### 核心思想
**这是本流程价值所在。**逐页面把原型、PRD、现有代码库摆在一起看，把不一致 / 缺失 / 矛盾全部摆到台面上，让开发者拍板。

### 做什么
逐页面遍历原型，每页生成三栏对照：

| 维度 | 原型表达 | PRD 描述 | 现有系统现状 | 处理决议 |
|---|---|---|---|---|
| 字段 / 列 | 原型展示了什么 | PRD 要求 | 接口已有？字段名？ | 复用 / 扩展 / 新增 / 待澄清 |
| 交互 | 点哪里、跳哪里、弹什么 | PRD 业务流程 | 现有路由 / 弹层组件 | 同上 |
| 状态 | 原型可能没画 | PRD 状态机 | 现有状态字典 | 同上 |
| 权限 | 原型可能没画 | PRD 权限矩阵 | 现有权限点 | 同上 |
| 边缘态 | 原型可能没画 | PRD 可能没写 | 现有同类页面怎么处理 | 实现 / 不做 |

### 三类必查的"缺口"
- **A. PRD 要而原型没画**：常见——错误态文案、无权限态、空数据态、超长截断、加载骨架、移动端布局、表单校验提示
- **B. 原型暗示而 PRD 没写**：常见——hover 效果、跳转目标、确认弹层文案、键盘交互（Enter 提交 / Esc 取消）、列表排序默认、图标含义
- **C. 当前系统没有，需要新建 / 改造**：常见——新接口、新字段、新菜单、新权限点、新组件变体、新枚举值

### 重点检查项（容易漏）
- [ ] 空态 / 加载态 / 错误态 / 无权限态（四态）每页都明确
- [ ] 移动端 / 响应式断点行为
- [ ] 表单：必填、长度、格式、异步校验、错误回显位置、提交防重
- [ ] 数据权限：列表过滤了，详情 / 导出 / 编辑也要过滤（参考 `06_安全规范.md`）
- [ ] 跳转目标：返回上一页 vs 返回列表 vs 关闭弹层
- [ ] 国际化：原型里的中文文案是否需要走 i18n
- [ ] 字典 / 枚举：原型上的标签是否对应系统字典，缺值要新增到 `docs/11_字典/`
- [ ] 时间 / 金额 / 百分比：开闭区间、时区、小数位、千分位（参考交付前自检清单 §3）

### 卡点规则
- ❌ 差异 / 缺口清单未产出 → **不进入 (3) 拆解映射**
- ❌ 清单中"待澄清"项未关闭 → **不进入开发**
- ❌ 开发者只说"嗯"、"知道了"（参见 CLAUDE.md §1）→ **不算确认**
- ✓ 开发者明确说"按这个清单做"等字样 → 更新 `docs/文档更新日志.md` 后进入下一步

### 产出
- 文件：`docs/02_功能设计/xx功能_原型对齐清单_yyyymmdd.md`
- **生成方式**：复制本文档末尾"附录：对齐清单填空骨架"代码块的内容，新建文件后逐项填写
- 内容：物料盘点 + 上述三栏对照表 + (3) 的两张映射表 + 处理决议（骨架已含全部段落）
- 与 100 (2) 实施方案的关系：本清单是实施方案的**前置输入**，不替代实施方案

## (3) 拆解映射

### 做什么
把原型拆成两张映射表，对应到现有代码库：

#### 表 A · 组件映射
| 原型区块 | 现有组件 | 处理方式 | 备注 |
|---|---|---|---|
| 顶部导航 | `<AppHeader/>` | 直接复用 | — |
| 数据卡片 | `<StatCard/>` | 扩展 prop（新增 trend） | 改动需向后兼容 |
| 高级筛选抽屉 | 无 | **新建** | 走 `04_前端开发规范.md` 组件规则 |
| 图标 X | `lucide-react/X` | 替换为系统图标库 | 不引入新图标库 |

#### 表 B · 数据 / 接口映射
| 原型字段（mock） | 真实接口 | 字段名 | 类型 / 枚举 | 处理方式 |
|---|---|---|---|---|
| `user.name` | `GET /api/users/:id` | `displayName` | string | 字段重命名 |
| `order.status` 标签 | `GET /api/orders` | `status` | 字典 `ORDER_STATUS` | 走字典翻译，禁止前端写死 |
| 趋势数据 | **无对应接口** | — | — | **新增**，走 100 §2 方案设计 |

### 红线
- ❌ 把原型的 mock 数据结构直接当成接口契约 —— **接口契约由后端规范主导**，原型字段需要映射、翻译、可能改名
- ❌ 把原型用的第三方组件 / 图标 / 字体直接引入项目 —— 先查项目已有依赖，避免重复轮子和包体膨胀
- ❌ 硬编码原型上的颜色 / 字号 / 间距 / 圆角 —— **必须走项目设计令牌**（无令牌时先沉淀令牌再写组件）

### 产出
- 把两张表追加到 (2) 的对齐清单文档，或并入 100 (2) 的实施方案文档

## (4) 分层落地

### 核心思想
**禁止一口气把"看起来跑通"的页面糊出来。**分三层，每层完成有明确自查。

### 第 1 层：静态骨架对齐原型
- 用项目设计令牌堆出页面骨架（HTML 结构 + 组件树 + 样式）
- 数据用占位 / 假数据，但**结构按表 B 的真实接口形态**，不照搬原型 mock
- 不接路由、不接状态、不接请求
- 自查：
  - [ ] 与原型并排，关键区块布局一致
  - [ ] 无硬编码颜色 / 字号 / 间距（grep 一下）
  - [ ] 用的都是表 A 标注的组件，无私自引入

### 第 2 层：接真实数据 / 状态 / 路由
- 接通表 B 的真实接口（已有的接，新增的按 100 §2 走方案）
- 接路由、URL 参数、查询参数同步
- 接状态机（PRD 描述的业务规则全部生效）
- 接表单校验（前端 + 后端双重，参考 `06_安全规范.md`）
- 自查：
  - [ ] PRD 的验收标准能跑通主流程
  - [ ] 浏览器 Console 无红错、无未捕获 Promise rejection
  - [ ] Network 面板正常路径无 4xx / 5xx

### 第 3 层：补齐边缘态 / 权限 / 国际化 / 响应式
- 四态：加载（骨架 / spinner）/ 空（图 + 文案 + 主动作）/ 错误（提示 + 重试）/ 无权限（友好提示，非 403 白屏）
- 权限：功能权限 + 数据权限（列表过滤的，详情 / 导出也要过滤）
- 国际化：所有面向用户的文案走 i18n
- 响应式：至少桌面 + 平板 + 移动三档不破版
- 自查：
  - [ ] 对照 `docs/90_最佳实践/交付前自检清单.md` §7 前端交互全勾
  - [ ] 对照 §4 权限与安全全勾

## (5) 双轨验收

### 视觉轨
- 关键页面与原型并排截图对比（桌面 + 移动）
- 偏差要么对齐、要么记录到对齐清单的"刻意偏差"小节并说明原因（如设计令牌差异、信息密度调整）

### 功能轨
- PRD 验收标准 / (2) 对齐清单的处理决议逐条勾选
- 验收标准是**可执行的测试步骤**，不是"流畅、友好"

### 卡点
- 两轨都过才进入 100 §6 测试 / 101 的回归测试

---

## 红线

- ❌ **还没出差异 / 缺口清单就动代码** —— 这是本流程的核心价值，跳过等于没走 105
- ❌ **像素级复刻原型但绕开设计系统**（硬编码 `#fff` / `font-size: 16px` / `margin: 24px`）
- ❌ **用原型的 mock 数据结构当作接口契约** —— 接口契约由后端 + API 规范主导
- ❌ **只实现原型画了的态，忽略空 / 错 / 无权限 / 加载**
- ❌ **报"已完成"但只跑了原型截图里那一种数据**
- ❌ **原型与 PRD 冲突时自己拍板** —— 必须先停下问开发者

---

## 注意事项

- **原型 ≠ 设计稿 ≠ 最终交付**：原型重在结构和流程，不要把原型的临时配色 / 临时图标当作最终视觉
- **原型展示的交互**（hover、弹层、动效、键盘）经常被开发忽视，(2) 必须显式列出
- **原型用的图标 / 字体 / 第三方组件**在系统中可能不存在，先评估替代方案，避免随意引入新依赖
- **多个原型页面共用一个新组件时**，组件应进入项目组件库 + 走 `04_前端开发规范.md` 的组件规则，而非散落在各页面
- **可观测性别忘记**：原型不会画日志和埋点，但落地代码必须按 `07_错误处理与日志规范.md` 补齐
