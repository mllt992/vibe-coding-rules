# 工作流 103 · 代码审查

## 触发后立即执行

1. **Read 完整工作流**：`docs/10_工作流程/103_代码审查工作流程.md`。
2. **识别审查模式**：
   - **模式 A · AI 自审**（100/101/102 开发完成后必跑）：四维度逐项过 + 产出审查报告
   - **模式 B · 人工审查 AI 产出**：AI 角色是**配合解释而非辩护**
3. **明确审查对象**：PR 链接 / commit / 文件清单。模糊时先问清楚。

## 四个维度（一个都不能省）

| 维度 | 重点 | 红线 |
|---|---|---|
| ① 正确性 | 业务逻辑 / 边界值 / 异常路径 / 事务边界 / 软删除 / 并发 | 最高优先级，不通过 = 阻断 |
| ② 规范性 | 对照 `docs/00_通用规范/` 各文件逐项检查 | 偏差需明确说明 |
| ③ 可维护性 | 单一职责 / 重复（三处以下不必抽象）/ 过度设计 / 魔法值 | YAGNI 优先 |
| ④ 安全性 | 鉴权 / 越权 / 输入校验 / 注入 / 敏感数据 / 依赖安全 | 对照 `06_安全规范.md` |

## 审 AI 产出代码的特殊关注点 ⚠️

AI 代码失败模式与人类不同，必须专门加这道筛（详见 `docs/90_最佳实践/AI能力边界与对策.md`）：

1. **API 是否真的存在** → 人类很少编造 API，AI 经常。grep 函数名 / 类名 / 配置项；版本敏感的 API 查官方文档
2. **逻辑是否有"跳跃"** → AI 代码常太流畅，警惕"诡异的简洁"和"if 块外的兜底无声覆盖"
3. **边界是否真处理** → 不是只 `// handle error`
4. **置信度有没有标注** → 全程肯定句没有任何不确定标记 = 警惕
5. **是否"过度复杂"** → 工厂模式 / 策略模式 / 抽象类堆砌
6. **注释是否在"自圆其说"** → 注释提到的边界，代码里真的实现了吗
7. **测试是否"哑测"** → `assertNotNull` 凑覆盖率
8. **是否"完成度伪装"** → "已测过" / "已更新文档"要拉证据看

## 红线

- ❌ **走过场审查**：看几个文件就 LGTM，无报告无证据
- ❌ **盲目套规范**：规范明显不适用本场景时应例外说明
- ❌ **批评不给建议**：指出问题必须给可行的修复方向
- ❌ **审查者甩锅**："是开发者写的与我无关" 不成立
- ❌ AI 审查者**与作者 AI 互相对夸**

## 审查报告

**必须产出**：`docs/04_代码审查/yyyymmdd_审查_xxx.md`（模板 `docs/20_模板/代码审查报告模板.md`）

**结论三档**：✅ 通过 / ⚠️ 修复后通过 / ❌ 不通过

**缺陷分类**：阻断（必修） / 重要（强烈建议） / 建议（可选）。阻断项**自己修完**再交付。

## 注意

- 代码审查**不能替代测试** → 走完审查仍需走 [workflow-testing](../workflow-testing/SKILL.md)
- 大 PR（> 500 行）→ 建议先拆分再审
- 审查是**逆向阅读**：假设代码错，去找哪里可能错
