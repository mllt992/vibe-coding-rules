# 工作流 103 · 代码审查（读代码，不跑代码）

## 触发后立即执行

1. **Read 完整工作流**：`docs/10_工作流程/103_代码审查工作流程.md`（开头有「分工速查」对照 104）。
2. **识别审查模式**：
   - **模式 A · AI 自审**（100/101/102 开发完成后必跑）：四维度逐项过 + 产出审查报告
   - **模式 B · 人工审查 AI 产出**：AI 角色是**配合解释而非辩护**
3. **明确审查对象**：PR 链接 / commit / 文件清单。模糊时先问清楚。

## 分工边界（103 vs 104）

| 议题 | 103 看（读代码） | 转 104 跑（不归本流程） |
|---|---|---|
| 权限 | 后端校验代码 / SQL 行级过滤 / 脱敏序列化层 | 构造越权请求实测 403 |
| 事务/并发 | 写法 / 乐观锁 / 唯一索引 / 消费者幂等代码 | 模拟并发提交断言结果 |
| 数据精度/日期/分页 | 代码层 SQL/后端/前端三端一致 | （不归 104） |
| 边界 | 代码里写没写处理分支 | 实际跑空数据/超长/大数据量 |
| 验收用例覆盖率 | （不归 103） | 验收标准转用例跑通 |

## 四个维度（一个都不能省）

| 维度 | 重点 | 红线 |
|---|---|---|
| ① 技术正确性 | 代码硬伤 / 数据精度跨端一致 / 事务并发写法 | 不通过 = 阻断 |
| ② 规范性 | 对照 `docs/00_通用规范/` 各文件逐项检查 | 偏差需明确说明 |
| ③ 可维护性 | 单一职责 / 重复（三处以下不必抽象）/ 过度设计 / 魔法值 | YAGNI 优先 |
| ④ 代码层安全 | 代码里**有没有写防线**：注入防护 / 鉴权代码 / 脱敏代码 / 依赖审查 | **实测越权归 104** |

## 审 AI 产出代码的特殊关注点 ⚠️

AI 代码失败模式与人类不同，必须专门加这道筛（详见 `docs/90_最佳实践/AI能力边界与对策.md`）：

1. **API 是否真的存在** → grep 函数名/类名/配置项；版本敏感的 API 查官方文档
2. **逻辑是否有"跳跃"** → 警惕"诡异的简洁"和"if 块外兜底无声覆盖"
3. **边界是否真"写"了代码** → 不是只 `// handle error`（**实测**归 104）
4. **置信度有没有标注** → 全程肯定句没有任何不确定标记 = 警惕
5. **是否"过度复杂"** → 工厂模式/策略模式/抽象类堆砌
6. **注释是否在"自圆其说"** → 注释提到的边界代码里真实现了吗
7. **测试代码本身质量** → 测试名是否清晰、断言强不强、是否哑测（**测试实跑情况**归 104）
8. **是否"完成度伪装"** → 拉证据看自检清单真勾过没

## 红线

- ❌ **走过场审查**：看几个文件就 LGTM，无报告无证据
- ❌ **盲目套规范**：规范明显不适用本场景时应例外说明
- ❌ **批评不给建议**：指出问题必须给可行的修复方向
- ❌ **替 104 做事**：本流程不跑功能、不实测权限、不验证业务流
- ❌ AI 审查者**与作者 AI 互相对夸**

## 审查报告

**必须产出**：`docs/04_代码审查/yyyymmdd_审查_xxx.md`（模板 `docs/20_模板/代码审查报告模板.md`）

**结论三档**：✅ 通过 / ⚠️ 修复后通过 / ❌ 不通过

**必含「遗留给 104 验证」清单**：本流程读代码无法判定、需要实测的项

**缺陷分类**：阻断（必修） / 重要（强烈建议） / 建议（可选）。阻断项**自己修完**再交付。

## 注意

- 代码审查**不能替代测试** → 走完 103 必须接着走 [workflow-testing](../workflow-testing/SKILL.md)，两者不可互替
- 大 PR（> 500 行）→ 建议先拆分再审
- 审查是**逆向阅读**：假设代码错，去找哪里可能错
- 遇到"必须跑才能验证"的疑点 → 不强行下结论，记到报告里转 104
