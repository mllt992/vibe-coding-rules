## 0. 项目基本情况

> 复制本套件后请在此处补充：技术栈、核心业务、代码主目录、运行方式、关键依赖版本。
> 信息越具体，AI 越不会乱猜。

- **技术栈**：（前端 / 后端 / 数据库 / 中间件 / 部署形态）
- **业务领域**：（一句话）
- **代码主目录**：（前端 / 后端）
- **文档主目录**：`docs/`
- **运行/调试**：（启动命令、端口、本地依赖）
- **关键依赖版本**：（库版本对 AI 防"用过时 API"很关键）
- **SQL 迁移目录**：（如 `migrations/` 或 `backend/db/migrations/` 或 `db/migrations/`，项目层一次性约定）
- **迁移工具**：（Flyway / Liquibase / Alembic / Prisma Migrate / Knex / 其他）
- **迁移文件命名**：（如 `V<yyyymmdd><序号>__<动作>_<对象>.sql`，示例 `V20260513001__create_xxx.sql`）
- **数据库变更设计归档**：`docs/02_功能设计/数据库变更/`（详见 [`106 数据库变更工作流程`](docs/10_工作流程/106_数据库变更工作流程.md)）

## 1. 三条铁律（不可违反）

1. **禁止瞎猜**——业务规则 / 字段含义 / API 契约 / 数据库结构 / 权限规则有不确定时，**先问再做**。具体三档处理见 [`docs/00_通用规范/09_AI协作规范.md`](docs/00_通用规范/09_AI协作规范.md) §六。
2. **改代码前先读规范**——查阅 [`docs/00_通用规范/`](docs/00_通用规范/) 对应规范文档；规范缺失或冲突时先与开发者对齐。
3. **动代码前先得明确确认**——超过"微改动"的任务必须先出方案，得到 **"开始 / 确认 / 同意 / 可以"** 等明确字眼才进入开发。"嗯""哦""知道了" **不算**。

## 2. 任务规模分级（决定走重流程还是轻流程）

收到指令后先按下表自我定级：

| 等级 | 判定 | 流程 |
|---|---|---|
| **微改动** | typo / 改文案 / 改颜色 / 单行调整，无业务规则变化，影响 1 个文件 | 直接做。无需方案、无需归档文档。仍需自跑一遍 + PR 简要描述。 |
| **小任务** | 单模块改动 / 无新增数据模型 / 无接口契约变化 / 全部改动 < 100 行 | 跳过需求分析与方案文档；仍要走自审清单 + 测试工作流 + 用户手册（如有用户感知）。 |
| **标准任务** | 新功能 / 优化升级 / 影响多模块 / 含数据库变更 / 含接口契约变更 / BUG 涉及关键路径 | 走完整对应工作流（100/101/102 → 103 → 104），全部归档。 |
| **高风险任务** | 涉及资金 / 鉴权 / 数据库迁移 / 公共组件 / 跨服务 / 生产数据修复 | 走标准任务 + 强制开发者预审方案 + 必须做回归 + 必须有回滚预案。 |

> 定级有疑问时**就高不就低**。不确定时走标准任务。

## 3. 工作流路由（按意图）

> 每个工作流既是文档（`docs/10_工作流程/`），也是 Claude Code skill（`.claude/skills/`）。Claude Code 看到对应意图会**自动加载 skill**，skill 内含触发警示并指向完整文档；其他 AI 工具仅靠下表 + CLAUDE.md。

| 意图 | 工作流文档 | Claude Code skill |
|---|---|---|
| 新增 / 新功能 | [`100`](docs/10_工作流程/100_新功能开发工作流程.md) | `workflow-new-feature` |
| 优化 / 升级 / 重构 | [`101`](docs/10_工作流程/101_已有功能优化升级工作流程.md) | `workflow-refactor` |
| BUG / 报错 / 异常 | [`102`](docs/10_工作流程/102_BUG修复工作流程.md) | `workflow-bug-fix` |
| 代码审查（读代码，不跑代码） | [`103`](docs/10_工作流程/103_代码审查工作流程.md) | `workflow-code-review` |
| 功能测试（跑功能，不读代码） | [`104`](docs/10_工作流程/104_测试工作流程.md) | `workflow-testing` |
| **有 HTML / Figma 原型 + (可选) PRD** | **前置 [`105`](docs/10_工作流程/105_原型协同开发工作流程.md)**，再回到 100 / 101 | `workflow-prototype` |
| **含数据库变更**（建表 / 加改字段 / 加改索引 / 数据迁移） | **前置 [`106`](docs/10_工作流程/106_数据库变更工作流程.md)**，再回到 100 / 101 / 102 | `workflow-db-change` |

意图模糊时**主动询问**，不要替开发者做决定。
多意图叠加时（"改 BUG 顺便加字段"）**强制拆分**串行处理。
**带原型的新增 / 改造**：105 是**前置增强**，先走 105 的"三方对齐"再进入 100 / 101，不替代它们。
**含 DB 变更的任务**：106 也是**前置增强**，先走 106 的"留痕设计 + 跨角色对齐"再进入 100 / 101 / 102，不替代它们。DB 变更默认按"高风险任务"处理。
**103 与 104 不可互替**：103 只**读代码**（技术正确性 / 规范 / 可维护性 / 代码层安全 / AI 失败模式）；104 只**跑功能**（验收用例覆盖率 / 业务流走查 / 权限和并发的实测 / 边界异常实测）。100 / 101 / 102 开发完成后**先 103 再 104** 串行走，跳过一个不算交付。两者职责重叠区已切干净——遇到"该归谁"疑问看各自文档头部的"分工速查"表。
**Claude Code 用户**可显式 `/workflow-bug-fix` 等强制触发；skill 自动触发依赖 description 关键词匹配，**本表是兜底**，不要因为有了 skill 就跳过路由判断。

详细规范索引：[`docs/索引.md`](docs/索引.md)

## 5. 强制完成定义（DoD）

任何工作流自称"完成"前，**逐条**对照 [`docs/90_最佳实践/交付前自检清单.md`](docs/90_最佳实践/交付前自检清单.md)，缺项 = 未完成。

速记：方案已确认 → 代码符合规范 → 已自审 → 关联文档已同步 → 测试已通过 → PR 描述清晰。

---

## 6. 红线（违反 = 工作未完成）

- ❌ 未获明确确认就改代码（"嗯"不算确认）
- ❌ 改业务关键代码却不读规范
- ❌ 顺手改任务范围外的代码（应记录到 [`docs/03_问题记录/技术债.md`](docs/03_问题记录/技术债.md)）
- ❌ 用"看起来对"取代"真跑通"
- ❌ 跳过自审清单 / 测试工作流
- ❌ 报"完成了"但有跳过的检查
- ❌ 在不熟悉的库上凭记忆写代码（**先查文档**，详见 AI 能力边界文档）

---

## 7. 沟通节奏

- 标准/高风险任务：**先发方案再开工**
- 每完成一个子步骤汇报一次进度
- 报错 / 卡点 / 与预期不符**立即抛出**
- AI 标注置信度：高/中/低/不确定，特别是关键决策点
