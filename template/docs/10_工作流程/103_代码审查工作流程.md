# 103 · 代码审查工作流程

> **触发条件**：开发者提出"审一下代码、Code Review、看看 PR"等意图；或工作流 100/101/102 完成开发后强制进入。
> **核心定位**：**代码视角的体检——只读代码，不跑代码。**
> **核心思想**：从**技术正确性、规范性、可维护性、代码层安全**四个维度审视代码本身的质量。
> **不在范围内**：业务功能能不能跑通、用户场景实际表现、权限实测能否拦住——这些归 [104 测试工作流程](104_测试工作流程.md)。

---

## 分工速查（103 vs 104，避免重复劳动）

| 议题 | 103 看什么（读代码） | 104 看什么（跑功能） |
|---|---|---|
| **权限** | 后端代码是否写了校验、SQL 是否有行级过滤、脱敏是否在序列化层 | 构造非所有者请求实测 403、跑出来看响应里是否真脱敏 |
| **事务 / 并发** | 写法是否在同一事务、外部调用是否卷入事务、写法是否有乐观锁/唯一索引、消费者代码是否幂等 | 模拟并发提交断言一次成功一次失败、MQ 重复投递断言不重复 |
| **数据精度 / 日期 / 分页** | 代码层 SQL/后端/前端三端是否一致；金额类型、时区处理、page 起始值 | （不归 104） |
| **边界处理** | 代码里是否**真的写了**空值/超长/异常分支（不是只 `// handle error`） | 实际跑空数据、超长输入、大数据量、网络断开 |
| **验收用例覆盖率** | （不归 103） | 需求验收标准是否逐条转测试用例并跑通 |
| **业务流走查** | （不归 103） | 关键业务流端到端实际操作一遍 |

> **两者关系是串行不可互替的双轨**：走完 103 ≠ 交付完成，必须接着走 104；跳过 103 直接 104，会漏掉规范性、可维护性、技术债。

---

## 审查角色与时机

| 触发场景 | 审查者 | 重点 |
|---|---|---|
| AI 完成开发后自审 | AI（本工作流必跑） | 四维度代码体检 |
| 开发者复审 AI 产出 | 人 | 代码风格契合度、规范遵循、可读性 |
| Pull Request | 同伴 + AI | 跨视角对照 |

## 审查的四个维度

### 维度一：技术正确性（最高优先级）

> 看代码是否会"自己出错"——纯代码层硬伤，与业务规则是否符合预期无关（后者归 104）。

#### 1.1 代码硬伤
- [ ] 类型错配 / 空指针 / 除零 / 数组越界
- [ ] 死循环 / 死锁 / 无限递归
- [ ] 资源未释放（文件句柄、连接、订阅、监听器、定时器）
- [ ] 错误处理：异常是否被吞掉？try-catch 范围是否过大？是否有 `catch {}` 空块？

#### 1.2 数据精度与跨端一致性（读代码即可查）
- [ ] **日期范围**：开闭区间在 SQL / 后端 / 前端三端**代码**是否一致（[start, end) vs [start, end]）
- [ ] **小数 ↔ 百分比**：转换只发生一次，无重复 × 100 / ÷ 100
- [ ] **金额**：后端用高精度类型（BigDecimal/Decimal），序列化为字符串避免精度丢失；前端千分位、等宽字体、右对齐
- [ ] **日期格式**：传输格式明确（建议 ISO-8601）；时区在边界层统一处理
- [ ] **分页**：page 起始（0 还是 1）前后端代码是否一致；`total / hasNext` 字段是否提供
- [ ] **排序**：默认排序字段稳定（必带 ID 作 tiebreaker），翻页不串行

#### 1.3 事务与并发（写法层）
- [ ] **事务边界**：跨表写入是否在同一事务内？外部 HTTP / MQ 调用**是否被卷入事务**？（要避免）
- [ ] **乐观锁 / 唯一索引 / 防重 token**：写入路径有没有写防线？
- [ ] **消息消费者**：代码层是否有幂等逻辑（去重表 / 业务键校验）？
- [ ] **软删除**：所有相关查询是否带 `deleted = false`？grep 一遍核对
- [ ] **唯一约束**：业务唯一性是否在 DB 层有索引保护？

> 上面三组都是**读代码就能查**的。"实际并发提交两次断言一次成功一次失败"是 104 的实测。

---

### 维度二：规范性

对照 [`docs/00_通用规范/`](../00_通用规范/) 逐项检查：

- [ ] **命名**：变量、函数、类、文件、目录是否符合规范？
- [ ] **代码风格**：缩进、空格、单文件长度、单函数长度、嵌套深度
- [ ] **注释**：注释是否在写"为什么"而不是"是什么"？无意义注释是否清理？
- [ ] **API 设计**：REST 路径、HTTP 方法、错误码、字段命名是否符合规范？
- [ ] **数据库**：表/字段命名、主键策略、索引、外键 / 软删除字段
- [ ] **错误处理与日志**：异常是否吞掉？日志级别是否正确？是否打印敏感信息？
- [ ] **Git 提交**：分支命名、提交粒度、提交信息

---

### 维度三：可维护性

- [ ] **单一职责**：函数/类是否做了太多事情？
- [ ] **重复代码**：相似代码块是否应该抽象？（注意：**三处以下重复不必抽象**）
- [ ] **逻辑一致性**：同一业务规则在多处出现时，代码表达是否一致？发现多处实现不一致是高危信号
- [ ] **过度设计**：是否引入了用不上的"灵活性"和"扩展点"？
- [ ] **魔法值**：硬编码字符串/数字是否应该提取常量？
- [ ] **依赖方向**：模块依赖是否符合分层架构？（如：业务层不能依赖控制器）
- [ ] **TODO/FIXME**：是否有遗留的临时代码、调试代码、`console.log`？

---

### 维度四：代码层安全

> 看代码里**有没有写防线**。**实际越权能不能拦住**是 104 的事。
> 对照 [`docs/00_通用规范/06_安全规范.md`](../00_通用规范/06_安全规范.md)。

- [ ] **鉴权代码**：未认证请求是否在中间件/守卫层被拒绝？token 校验是否实现？
- [ ] **授权代码**：功能权限校验是否在**后端代码**（不是只在前端隐藏）？
- [ ] **数据权限代码**：行级过滤是否在 **SQL 层**（不是 Service 内存过滤）？
- [ ] **输入校验代码**：参数校验是否在后端**写了**？仅前端校验视为无效
- [ ] **注入防护**：SQL 拼接、命令拼接、模板拼接是否使用参数化方式？
- [ ] **敏感数据脱敏**：密码、token、身份证、手机号在日志/响应中是否脱敏？脱敏是否在**序列化层**（不是依赖前端隐藏）？
- [ ] **依赖安全**：新增的第三方库是否经过基本审查（来源、维护状态、license）？

> "构造其他用户 ID 实测能否读到不该读的数据" → 104。本流程只检查"代码里有没有这道防线"。

## 审查的两种模式

### 模式 A：AI 自审（必跑）

AI 在工作流 100/101/102 的"代码自审"步骤进入本工作流。
执行：
1. 对照本文 §维度一~四 逐项过一遍
2. 缺陷分类：
   - 阻断（必修，否则视为未完成）
   - 重要（强烈建议修）
   - 建议（可选改进）
3. 输出**审查报告**到 `docs/04_代码审查/yyyymmdd_审查_xxx.md`（模板见 `docs/20_模板/代码审查报告模板.md`）
4. 阻断项**自己修完**再交付；重要项与开发者商量是否当前修
5. 走完 103 后**继续走 104**——本流程不验业务功能

### 模式 B：人工审查 AI 产出

开发者审查 AI 代码时，AI 的角色是**配合解释而不是辩护**：
- 开发者指出问题 → AI 先理解再回应
- 不理解时反问澄清，不要假装理解
- 修改后**再次自审**整遍，不要只盯着被指出的一处

---

## 审查的红线

- ❌ **走过场审查**——只看了几个文件就 LGTM，无报告无证据
- ❌ **盲目套规范**——规范明显不适用本场景时应该例外说明，而不是硬套
- ❌ **审查者甩锅**——审过的代码出问题，审查者也有责任
- ❌ **批评不给建议**——指出问题时要给出可行的修复方向
- ❌ **替 104 做事**——本流程不跑功能、不实测权限、不验证业务流；遇到这类问题记录到审查报告并标"待 104 验证"

## 审查 AI 产出代码的特殊关注点 ⚠️

> AI 产出的代码与人类写的代码**失败模式不同**。审查时要专门加这一道筛。
> 详细背景见 [`docs/90_最佳实践/AI能力边界与对策.md`](../90_最佳实践/AI能力边界与对策.md)。

### 关注点一：API 是否真的存在

**人类很少编造 API**，**AI 经常**。

- [ ] 用了陌生/新/小众库的代码：**真跑一遍**或查官方文档确认 API 签名
- [ ] 调用的函数名 / 类名 / 配置项在仓库或依赖中 grep 得到
- [ ] 版本敏感的 API：当前项目用的库版本支持这个 API 吗？
- [ ] 链式调用 / 流式 API：每一步返回类型对得上吗？

**经典陷阱**：AI 把 A 库的方法名错配到 B 库（如把 axios 的 `.get(url, { params })` 写成 fetch 的用法）。

### 关注点二：逻辑是否有"跳跃"

**人写代码有思考痕迹**（注释、命名变化、临时变量）；**AI 代码常常太流畅**——流畅到把"我想到了"和"我做到了"之间的思考链跳过去。

- [ ] 复杂业务规则：AI 是否真的写了所有分支的代码，还是看似处理实则只走主路径？
- [ ] 状态机推进：每个状态的转入/转出条件代码都对吗？
- [ ] 条件嵌套：嵌套深处的逻辑是否经得起推敲？
- [ ] **诡异的"简洁"**：本应复杂的逻辑被写得过于简单——警惕"AI 把难题轻易抹掉了"
- [ ] **条件分支与兜底语句并存时**：兜底语句是不是在 if 块外永远执行，把条件内的结果"无声地"覆盖了？典型场景：`if (ok) router.push(x); router.replace('/')` —— 第二行永远把第一行盖掉。AI 在改造旧代码时特别容易留下这种残留。

### 关注点三：边界是否真的"写"了代码

AI 倾向"happy path 完美主义"——主路径写得漂亮，边界轻描淡写：

- [ ] 空值 / null / 空数组 / 零 / 负数 / 超大 / 超长 的处理代码是否真的写了
- [ ] 异常路径有没有真的写代码（不是只 `// handle error` 注释占位）
- [ ] 默认值是否安全（不是 0 / null / "" 含糊带过）
- [ ] 并发场景的写法是否真的考虑了

> 边界**实际表现**归 104；本流程只查代码里写没写处理分支。

### 关注点四：置信度有没有标注

- [ ] AI 是否标注了"这部分我确定 / 这部分我假设"
- [ ] 假设是否在 PR 描述或代码注释中明示
- [ ] 对陌生库的使用，AI 是否说明"已查文档"还是"凭记忆"

如果**全程都是肯定句没有任何不确定标记**——警惕。真实工程不存在 100% 确定。

### 关注点五：是否"过度复杂"

AI 容易把简单问题包装得很专业（工厂模式、策略模式、抽象类...）：

- [ ] 引入的抽象层是否真有必要？还是 YAGNI？
- [ ] 设计模式名词出现 → 反问"不用这个能不能做到"
- [ ] 大量 try-catch / 防御性编程 → 反问"这些异常真的可能发生吗？"

### 关注点六：注释是否在"自圆其说"

AI 的注释有时是为了让代码"看起来合理"，而不是真的解释：

- [ ] 注释是否描述了真实意图？还是只复述了代码？
- [ ] 注释提到的边界 / 业务规则，**代码里真的实现了吗？**
- [ ] 注释是否引用了不存在的需求 / 不准确的文档？

### 关注点七：测试代码本身的质量

> 注：测试是否真的"测过业务"是 104 的事；本节只审"测试代码本身写得好不好"。

- [ ] 测试名是否清晰描述了行为？
- [ ] 断言是否真的检查关键结果（不是 `assertNotNull`）？
- [ ] 测试数据是否合理（不是只测了 happy path 的"魔法数据"）？
- [ ] 测试代码结构是否清晰（Given/When/Then）？

### 关注点八：是否"完成度伪装"

- [ ] AI 自称"完成"——`docs/90_最佳实践/交付前自检清单.md` 真的逐条勾过吗？
- [ ] AI 说"已测过"——拉一下测试日志看真跑没跑（**实跑验证归 104**）
- [ ] AI 说"已更新文档"——真去对应位置看了吗
- [ ] AI 跳过的步骤是否在 PR 描述中明示理由

### AI 审查者审查 AI 代码

如果审查者本身也是 AI：
- 不要被"同伴的流畅"催眠
- **更怀疑、更具体**——找具体行号说问题
- 优先看"逻辑跳跃"和"边界写没写代码"——这是 AI 间互审最容易盲的地方
- 不与作者 AI 互相"对夸"

## 审查报告

### 产出位置
`docs/04_代码审查/yyyymmdd_审查_xxx.md`

### 必含内容
- 审查对象（PR 链接 / commit / 文件清单）
- 维度一/二/三/四的检查结果
- 缺陷清单（按阻断/重要/建议分类）
- **遗留给 104 验证的项**（本流程读代码无法判定，需要实测的）
- 结论：✅ 通过 / ⚠️ 修复后通过 / ❌ 不通过
- 后续动作清单

## 自检（审查者用）

- [ ] 四个维度都检查过，**不是只看了一两个维度**
- [ ] 通读了核心改动（不只是看了 diff 摘要）
- [ ] 关键路径在脑中跑通了，包括异常分支（**实际跑过归 104**）
- [ ] 跨文件影响已确认（grep 搜被改动符号/接口/表）
- [ ] 审查报告已落盘
- [ ] 已提醒"104 必须接着走"

## 注意事项

- **代码审查不能替代测试** —— 走完 103 必须走 104，两者职责不重叠也不互替
- **审查是逆向阅读** —— 不假设代码对，假设它错，去找它哪里可能错
- **审查也要审"没写的代码"** —— 该有的边界处理、该有的日志、该有的测试用例有没有？
- **大 PR 是审查的最大敌人** —— 收到 >500 行变更的 PR，建议先拆分再审
- **遇到"必须跑才能验证"的疑点** —— 不要在 103 强行下结论，记到报告里转给 104
