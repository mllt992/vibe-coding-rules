# 106 · 数据库变更工作流程

> **触发条件**：任务涉及任一项即触发本流程——
> - DDL：新建表 / 加字段 / 改字段类型 / 改字段长度 / 加/删/改索引 / 加/删约束 / 改默认值 / 改 COMMENT
> - 大体量 DML：数据回填、清洗、迁移（影响行数 > 1w 或涉及关键业务表）
> - Schema 重命名 / 移动 / 拆库拆表 / 归档 / 删表
>
> **核心思想**：**数据是项目最稳定也最难变更的部分。** 一个偷懒的字段、一次没演练的迁移，会在三个月后让全员加班。
> 本流程通过 **"设计先行 → 跨角色对齐 → 演练 → 灰度"** 四道关卡，让 DB 变更可追溯、可回滚、可审计。
>
> **与 100 / 101 的关系**：本流程是**前置增强**，不替代它们（类似 [`105`](105_原型协同开发工作流程.md) 对原型的角色）。
> - 新功能含 DB 变更：先走 106 (1)~(5)，再回到 100 后续步骤
> - 已有功能改造含 DB 变更：先走 106 (1)~(5)，再回到 101 后续步骤
> - 纯 BUG 修复涉及 DB 字段：先走 106 (1)~(3)，方案确认后并入 102
>
> **适用任务等级**（按 [`CLAUDE.md §2`](../../CLAUDE.md) 定级）：
> - **DB 变更默认按"高风险任务"处理**（CLAUDE.md §2 已明确"数据库迁移"属高风险）
> - 例外：只新增 COMMENT、只改字典枚举值（不涉及结构）、只加纯辅助索引（小表）—— 可降为标准任务
> - 涉及主表、跨服务表、金额表、鉴权表 —— **强制高风险**


## (1) 定级 + 物料盘点

### 做什么
- 按"触发条件"对照本次变更是否需要进入 106
- 按本工作流前言判定等级：标准 / 高风险（**就高不就低**）
- 物料盘点：
  - 关联需求文档路径（无关联则记录"内部技术变更"并说明）
  - 现有同表的历史迁移文件（grep 表名）
  - 现有规范的偏差预判（先翻 [`03_数据库设计规范.md`](../00_通用规范/03_数据库设计规范.md)）
  - 涉及表的"数据归属"：归哪个领域 / 服务，谁有写权限

### 缺料即停
- 业务规则不清（"这个字段啥时候为 NULL？"）→ 问业务方
- 历史迁移对当前结构有什么影响不明 → 查迁移历史，必要时问 DBA
- 数据归属不明（这表是哪个服务的）→ 问架构师

### 产出
- 在 (2) 的设计文档"元信息"小节登记定级、归属

## (3) 跨角色对齐 ⚠️ 卡点

### 核心思想
**这是本流程的最高价值点。**DB 变更影响面比一般代码大得多，必须让相关角色都看过。

### 做什么
- 把 (2) 的设计文档发给相关角色，按下表逐项过：

| 角色 | 必看 | 说明 |
|---|---|---|
| 业务方 / 产品 | §1、§3.4 字段语义 | 业务表达完整、字段含义无误 |
| 后端开发 | §3、§4.1、§5.2 查询 | ORM 怎么改、新接口怎么写 |
| 前端开发（如涉及） | §3.4、§4.1 | 字段类型/枚举/PII 影响前端 |
| DBA | §3.2 DDL、§5、§6、§7 | 索引、锁、容量、迁移演练 |
| 数据团队（如涉及） | §3.4、§4.2 血缘 | 同步任务、报表影响 |
| 安全 / 合规（如涉及 PII / 资金 / 鉴权） | §3.4 PII、§8 | 脱敏、加密、审计 |
| 运维 | §6 迁移、§7 演练 | 发布顺序、备份、监控 |

### 卡点规则
- ❌ 任何角色"待确认" → **不进入 (4) 写迁移**
- ❌ 高风险变更未经 DBA 评审 → **不进入 (4)**
- ❌ 涉及 PII 未经安全 / 合规评审 → **不进入 (4)**
- ❌ 跨服务表未通知下游服务 owner → **不进入 (4)**
- ❌ 开发者只说"嗯""知道了"（[CLAUDE.md §1](../../CLAUDE.md)）→ 不算确认
- ✓ §9 表格签字齐全，明确字眼（"同意 / 可以 / 通过"）→ 进入下一步

### 产出
- 设计文档 §9 跨角色对齐表更新签字
- [`文档更新日志.md`](../文档更新日志.md) 记一条"冻结"

## (4) 迁移文件 + 回滚脚本

### 做什么
- **迁移 SQL 写到 [`CLAUDE.md §0`](../../CLAUDE.md) 声明的目录**（不允许临时 SQL 散落）
- 文件头按 [`03_数据库设计规范.md §三再补.2`](../00_通用规范/03_数据库设计规范.md) 填元信息（关联设计、关联需求、风险等级、回滚脚本）
- **所有字段含中文 COMMENT**（PII 字段含标记）—— 是 [`03_数据库设计规范.md §三补`](../00_通用规范/03_数据库设计规范.md) 的强制要求
- 大表 ALTER 走分步：见 [`03_数据库设计规范.md §七`](../00_通用规范/03_数据库设计规范.md) "危险操作的安全做法"
- 数据回填脚本：带 `LIMIT` / 分批 / 幂等 / 事务保护
- **同步写 down 脚本**（或显式"不可回滚"声明 + 理由）

### 双向链接自查
- [ ] 设计文档 §6.1 "迁移文件清单"列出了所有迁移文件名
- [ ] 每个迁移文件头部含"关联设计: docs/02_功能设计/数据库变更/xxx.md"
- [ ] 留痕断链 = 工作未完成

### 红线
- ❌ 迁移 SQL 不含 COMMENT
- ❌ 大表 ALTER 直接一步到位（应分步）
- ❌ 数据回填没 LIMIT 没事务保护
- ❌ DROP / RENAME 没注释为什么
- ❌ 把"down 脚本太麻烦不写了"当合理理由

## (5) 演练

### 在哪演练
- 优先：等量副本（生产数据 dump → 脱敏 → 灰度库）
- 备选：缩量副本（≥ 生产 10%），但必须明确风险
- ❌ 禁止：只在空库 / 开发机上演练就上线

### 演练什么
- [ ] up 全套：建表 + 加字段 + 索引 + 回填 → 记录耗时与锁时长
- [ ] down 全套：能完整回退到变更前状态
- [ ] 回填脚本：实际数据量下跑通，分批大小合理
- [ ] 灰度抽样：跑设计文档 §5.2 列出的所有高频查询，`EXPLAIN` 命中预期索引

### 产出
- 设计文档 §7 演练记录表填写完整

### 卡点
- ❌ 演练失败或耗时超预期 → 回 (4) 调整方案，**不允许上线**
- ❌ 演练未覆盖 down → **不允许上线**

## (7) 灰度发布 + 上线验证

### 发布顺序
- **必须明确**：先迁移还是先代码？为什么？
- 默认顺序（按字段加法 / 减法不同）：
  - **加字段 / 加索引（兼容性）**：先迁移 → 再发代码
  - **删字段 / 改类型（破坏性）**：先发代码停止使用 → 观察 → 再迁移删除
  - **数据回填**：迁移到位后单独执行，不卷入应用发布

### 上线后观察期
- 至少 **1 周观察**：监控、慢查询、日志、业务指标
- 观察清单：
  - [ ] 慢查询有无新增（阈值见各项目）
  - [ ] 错误日志（特别是 ORM 报错、约束冲突）
  - [ ] 业务指标（订单量、用户量、关键转化）无异常下跌
  - [ ] 下游消费方报告（数仓、报表、对账）无异常

### 回滚触发条件
- 满足任一即触发：业务异常率上升 / 关键查询超时 / 数据一致性问题 / 下游消费方报错
- 按设计文档 §6.4 "回滚预案" 执行

### 产出
- 设计文档 §12 "实施后回填"补完
- 进入 [`100 §6 测试`](100_新功能开发工作流程.md) / [`101 回归`](101_已有功能优化升级工作流程.md) / [`103 审查`](103_代码审查工作流程.md) / [`104 测试`](104_测试工作流程.md)
- 回归用例新增到 [`docs/05_回归用例/`](../05_回归用例/)（特别是金额、状态机、对账类）

## 红线（违反 = 工作未完成）

- ❌ **未出设计文档就写迁移 SQL** —— 留痕缺失，回头查"为什么这么改"找不到答案
- ❌ **字段无中文 COMMENT** —— 违反 [`03_数据库设计规范.md §三补`](../00_通用规范/03_数据库设计规范.md)
- ❌ **跨角色对齐表有"待确认"就开工** —— (3) 卡点形同虚设
- ❌ **没演练就上生产** —— DB 变更是单向门，一次失败影响全员
- ❌ **没有 down 脚本** —— 出问题只能硬上，无回滚能力
- ❌ **直连生产 DB 改结构** —— 跳过迁移工具 = 无审计 / 无版本 / 无重放
- ❌ **PII 字段不脱敏 / 不加密 / 不标记** —— 合规风险
- ❌ **跨服务表变更不通知下游** —— 隐式破坏契约
- ❌ **设计文档与迁移文件不互链** —— 单向门变信息黑洞

---

## 注意事项

- **"只是加个字段"是最容易掉以轻心的场景**：默认值、空值处理、回填、下游同步任一项漏了都可能炸
- **大表 ALTER 不要凭直觉**：拿真实数据量演练，DBA 看一眼可能省你半天
- **"等会儿手动 INSERT 一行测试数据"** = 走迁移文件，不要在控制台 hack
- **回滚脚本要真的测试**（演练 (5) 必须包含 down），不要只写不验
- **多个相关变更**：能一次方案 + 多个迁移文件，**不要拆成多个方案**，否则关联性丢失
- **字段语义变更 = 一次变更**：不要"先改 DB 后想起来更新字典"，必须同批次
