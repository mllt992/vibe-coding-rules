# 如何向 AI 提需求（开发者侧 vibe coding 指南）

> 套件的其他文档都在约束 **AI**。本文档约束 **开发者**自己——
> 你怎么发指令，决定了 AI 能做出什么。

---

## 一、核心心智：AI 是"超级实习生"

把 AI 想成一个**聪明但完全不了解你项目的实习生**：
- 业务背景他不懂——要讲
- 项目约定他不知道——要写进 CLAUDE.md
- 你脑子里"显然如此"的东西他不显然
- 但他读规范、写代码、写文档的速度比你快 10 倍

**好的指令 = 上下文 + 目标 + 边界 + 验收**

## 二、好需求 vs 烂需求对照

### 烂例 1：太宽泛

❌
```
做个用户管理系统
```

✅
```
做用户管理模块的"用户列表 + 创建用户 + 编辑用户"三个页面。
不做：用户角色与权限分配（独立任务）、用户头像上传（独立任务）。
角色：超级管理员可看全部、可改全部；普通管理员只能看自己组的、只能改未删除的。
字段：用户名（唯一）、姓名、邮箱、手机、所属组、状态、备注。
状态：在用 / 锁定 / 已停用 / 已注销。
进入 100 工作流。
```

**差距**：明确的范围、非范围、角色、字段、状态、入口工作流。

---

### 烂例 2：动词模糊

❌
```
优化一下订单查询
```

✅
```
订单查询接口当前在数据 10w 行时 P95 = 3s，目标降到 < 500ms。
当前 SQL 见 OrderRepository.search()。
不允许改前端接口契约。
进入 101 工作流。重点是回归测试。
```

**差距**：可量化目标 + 边界约束 + 入口工作流。

---

### 烂例 3：状态描述不完整

❌
```
保存按钮点了没反应，修一下
```

✅
```
BUG：用户管理 → 新建用户 → 点保存按钮无任何反应。
复现：账号 testadmin / 密码 xxx；进入用户管理；点新建；填字段（用户名 a/姓名 a/邮箱 a@a.com）；点保存。
实际：按钮变灰 0.5s 后恢复，无任何提示，列表无新增。
期望：保存成功后关闭弹窗、刷新列表、显示新用户。
浏览器 Console 报错：见附件截图。
Network 显示 POST /api/v1/users 状态 200，但 body 是 {"success": false, "code": "VALIDATION_ERROR"}。
进入 102 工作流。
```

**差距**：复现步骤、实际行为、期望行为、技术线索（Console、Network）。

### 烂例 4：连续指令缺锚点

❌（在长会话里）
```
对了，那个加一下导出功能
```

✅
```
（新会话）
背景：我们刚做完用户列表的查询和分页（见 docs/02_功能设计/用户管理_实施方案_20260513.md）。
现在加用户列表的导出功能。
要求：
- 导出当前筛选条件下的全部数据（不只是当前页）
- 走后端流式生成，前端只点击下载
- 格式 Excel
- 权限：user:export
- 数据权限沿用列表的过滤规则
进入 100 工作流，但因为基于已有方案，可走"小任务"轨（跳过单独需求分析，直接进入方案）。
```

**差距**：新会话起头、关联已有产出、明确边界、引用工作流。

## 三、好指令的最小结构

无论任务大小，建议每次指令至少含：

```
[背景]      为什么要做？关联什么需求/BUG？
[目标]      具体做什么？可量化吗？
[范围]      做什么 / 不做什么
[约束]      技术、性能、兼容性、权限的硬性要求
[入口]      进入哪个工作流（100/101/102），或是否走轻量轨
[预期产出]  你期望我交付什么？文档？代码？测试？
```

**小任务**：5 行也够。
**大任务**：每项写 2-3 行。

## 四、何时贴什么

| 任务类型 | 该贴 |
|---|---|
| BUG 修复 | 复现步骤、Console 截图、Network 请求/响应、相关日志 |
| 性能优化 | 当前指标、目标指标、相关 SQL / 慢日志、调用链 |
| 新功能 | UI 稿、PRD、字段清单、状态机、权限矩阵 |
| 接口变更 | 老接口契约、调用方清单 |
| 重构 | 现有代码片段、痛点描述、不可破坏的外部行为 |

**通用原则**：能让 AI 少猜的信息，都值得贴。

## 五、如何识别 AI 在"瞎编"

### 信号
- **API 名陌生**：使用的函数你没见过、文档里也搜不到
- **代码太流畅**：复杂逻辑一遍写就过，没有思考痕迹
- **不标置信度**：所有结论都是肯定句
- **抗拒查证**：你说"你查一下文档"，AI 说"我确定是这样的"
- **解释自洽过头**：解释每一个细节，但每个细节都没法验证
- **太多 try-catch**：用大量异常处理掩盖逻辑不确定

### 验证手段
1. **跑一下**：能跑通是底线
2. **查文档**：陌生 API 直接搜官方文档
3. **反问**：让 AI 列出"如果 X 实际上不是 Y，会发生什么"
4. **重做**：让 AI 用另一种方式实现同一逻辑——两种方法相互印证

## 六、阶段性指令的发法

大任务不要一句话扔过去，分阶段：

```
阶段 1：先帮我把需求分析写出来
  → 等 AI 输出
  → 你审 / 给反馈
  → 确认进入下一阶段

阶段 2：基于确认的需求，给方案设计
  → 等 AI 输出
  → 你审 / 给反馈
  → 确认进入下一阶段

阶段 3：方案确认后，开始开发
  → ...
```

**每个阶段都有"卡点"——你不开口确认，AI 不动**。
这正是工作流设计的核心。

## 七、对 AI 不满意时怎么办

### 不要这样

❌ `这不对，重做`（信息量为 0，AI 不知道哪里不对）
❌ `算了你别做了，我自己来`（放弃合作但没纠错，AI 下次还错）
❌ `你怎么连这个都不会`（情绪化无效）

### 应该这样

✅ **指出具体错处 + 给出正确方向 + 让 AI 复述理解**

```
你写的 OrderService.cancel 里调用了 paymentClient.refund() —— 这是同步 HTTP 调用，
但它在 @Transactional 方法里。这违反了 docs/00_通用规范/05_后端开发规范.md §4 的
"事务里禁止外部调用"。

正确做法：把退款发到消息队列异步处理，或用 Outbox 模式与本事务一起持久化。

请先复述一下这个错误的根本问题在哪，再修改。
```

## 八、关于"嗯"

**"嗯"不是确认。**
**"OK"勉强算确认。**
**"开始 / 同意 / 可以 / 没问题 / 干吧"是确认。**

工作流要求 AI 等明确确认。所以**你也要明确表态**——
模糊的应答 = AI 还在等 = 时间在浪费。

---

## 九、关于"再快一点"

你说"再快一点"，AI 听到的是"跳过繁琐步骤"。
跳过的通常是：测试、自审、文档。**这些恰恰是你需要的**。

需要快的时候，**指定走"轻量轨"**：
```
这次走小任务轨：跳过方案文档，直接改。但自审清单还是要走。
```

而不是说"快一点"。

## 十、会话长度的红线

| 会话状态 | 建议 |
|---|---|
| < 30 分钟，主题专注 | 继续 |
| 30 分钟～2 小时，单主题 | 继续，但定期让 AI 总结现状 |
| > 2 小时 OR 反复同错 OR 已偏题 | **起新会话** |
| 多个不相关任务 | **每个任务一个新会话** |

长会话的最大成本是"上下文漂移"——AI 可能忘了一开始的约定。
起新会话的成本是"重新解释背景"——但 CLAUDE.md 已经自动加载了一大半。

---

## 十一、与 AI 的元沟通（关于沟通的沟通）

可以直接告诉 AI 你的偏好：

```
- 你回复时不要每次"好的，让我..."开头，直接进入正题
- 你产出文档时不要写废话注释
- 你不确定时直接说"不确定"，不要装
- 我说"嗯"不是同意，我说"开始"才是同意
```

这些会成为本会话的约定。**如果是长期偏好，写进 CLAUDE.md。**

## 十二、自我训练：写完指令后自检

```
[ ] 我有没有交代背景？
[ ] 我的目标是否可量化 / 可验证？
[ ] 我有没有明确"不做什么"？
[ ] 我有没有指定工作流入口？
[ ] 我贴的信息够 AI 不靠猜就能开工吗？
[ ] 我用的是不是"开始 / 确认 / 同意"等明确字眼？
```

---

## 十三、记住

**你不是在用 AI**，你**在和 AI 协作**。
你越尊重协作流程，AI 越能稳定输出。
你越随意，AI 越随意。

vibe coding 不是放任 AI，而是**用清晰的规则让 AI 进入 flow 状态**。
